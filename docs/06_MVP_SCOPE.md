# CanadaCare — MVP Scope

**Status:** Proposed academic prototype scope  
**Version:** 0.1  
**Last updated:** 2026-09-17

## 1. MVP objective

Demonstrate, using **synthetic data only**, how a patient-facing interface and authorized coordinator workflow could present referral status and manage a small, explicitly defined appointment-coordination scenario.

The MVP is a proof of concept, not a production healthcare service, clinical system, or claim of regulatory compliance.

## 2. Scope selection gate

Before implementation, choose and document:
- One Ontario region or a clearly simulated environment.
- One service line / referral pathway.
- One patient journey and one operational user journey.
- A specific coordination problem supported by discovery evidence.
- A small set of approved status and eligibility rules.
- What existing system the prototype is intended to complement.

A diagnostic imaging pathway is one candidate for research, not a predetermined choice.

## 3. In scope (candidate)

### Patient interface
- Sign in using a development identity provider with synthetic test accounts.
- View synthetic referral records assigned to that test patient.
- See plain-language status, last-updated time, and next step.
- View a mock appointment offer and accept/decline it in the demonstration workflow.
- View notification history generated by the prototype.

### Coordinator interface
- View synthetic referral queue.
- Update permitted workflow statuses.
- Create or publish a mock appointment offer.
- Record offer outcome and audit event.
- See basic queue counts for demonstration.

### Backend
- Spring Boot REST API.
- PostgreSQL with synthetic seed data.
- Server-side authentication and authorization.
- Input validation and consistent error responses.
- Audit events for sensitive or consequential actions.
- Basic integration adapter or simulator, only if useful to demonstrate the chosen hypothesis.

### Frontend
- React + Vite + Tailwind CSS.
- Patient and coordinator routes/views.
- API client separated from UI components.
- Accessible labels, keyboard navigation, responsive layout, and clear loading/error states.

## 4. Out of scope

- Real personal health information (PHI) or live patient accounts.
- Production connection to hospital, provincial, or vendor systems.
- Real appointment booking or modification.
- Clinical triage, diagnosis, treatment recommendations, or automated prioritization.
- Claims that the system is PHIPA-compliant or certified.
- Payments, insurance claims, or broad national rollout.
- AI-based clinical decisions.
- Guaranteed wait-time reduction.
- Replacing EMRs, HIS, existing patient portals, eReferral, or central intake systems.

## 5. Candidate user stories

1. As a synthetic patient, I can view the status and next step for my referral.
2. As a synthetic patient, I can view a mock appointment offer and record a response.
3. As an authorized coordinator, I can view the synthetic queue for my organization.
4. As an authorized coordinator, I can update a permitted status and see that the action was recorded.
5. As a security reviewer, I can inspect audit events for selected sensitive actions.
6. As a project evaluator, I can run a scripted end-to-end demonstration using seeded synthetic records.

## 6. Acceptance criteria

- A patient test account cannot retrieve another patient's referral.
- A coordinator can access only the synthetic organization/work queue assigned to their role.
- Invalid status transitions are rejected by the backend.
- All sensitive/consequential prototype actions create audit records.
- The UI distinguishes mock offers from real appointments.
- API errors do not expose stack traces, secrets, or unnecessary personal data.
- Demo data is clearly synthetic and contains no real patient details.
- Core workflow can be demonstrated from a clean setup using documented steps.
- Basic automated tests cover authorization boundaries and core workflow rules.

## 7. Proposed stack

| Layer | Choice |
|---|---|
| Frontend | React + Vite + Tailwind CSS |
| Backend | Java + Spring Boot REST API |
| Database | PostgreSQL |
| Identity | Keycloak / OIDC for development |
| Integration | Simulated adapter; HAPI FHIR only if required by the selected demo |
| Packaging | Docker Compose |
| Tests | JUnit, Mockito, API tests, Playwright or Cypress |
| Security checks | Dependency scanning, secret scanning, OWASP-oriented review |

Keep the prototype as a modular monolith unless discovery demonstrates a real need to split services.

## 8. Definition of done

- User story and acceptance criteria reviewed by the team.
- Code reviewed and merged through version control.
- Automated tests pass.
- Authorization and validation tests cover the change.
- No real PHI or secrets committed.
- API and UI behavior documented.
- Known limitations recorded.
- Demo tested from a clean environment.
